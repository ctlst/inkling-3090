# Quantized KV on Inkling 2 Mini

Unsloth’s merged change enabled Q8_0/Q4_0 K/V inside its banded relative-attention kernel. The previous CUDA path could reserve an additional F16 K/V copy when quantized cache fell back to dense attention. It also duplicated mask work across layers. Their release bundled that fix with graph deduplication, short-row matrix/vector packing, fused row clipping and fused SiTU. Their 2,858 → 4,561 tok/s result measures 512-token prefill on the UD-IQ1_S weights on one B200. The 47.8 → 66.4 tok/s result uses two GPUs. At 1M context they report Q8_0 peak device memory falling from 34,838 to 27,628 MiB. The same table lists the old F16 peak at 50,308 MiB. Across all four listed lengths, old Q8 already used less total device memory than old F16. The table demonstrates a 7.04 GiB improvement at 1M with Q8; it does not reproduce a reversal between Q8 and F16. Their old/new build tests reported zero mean KLD on selected configurations; quantized KV against an F16 reference still measured about 0.0027. [Unsloth measurements and conditions](https://github.com/unslothai/llama.cpp/pull/399)

Our historical llama.cpp IQ4_NL measurements used upstream build b12600, Q8_0 keys and values, and plain decoding. They predate these Unsloth changes. A current fork comparison needs a fresh run with the same compatible weights, power conditions, context, draft setting and cache policy.

The released SM86 vLLM decode path already consumes paged E4M3 storage. In a saved Nsight Compute replay at 196,608 tokens, the eight target verification positions shared a tile: 384.59 MiB of device DRAM reads for 384 MiB of unique K/V, including ancillary reads. The measurement is for one full-attention kernel invocation.

Long prefill has a different implementation. Eligible 512-token full-attention chunks at or above 65,536 history tokens stage groups of up to 16,384 older tokens for FlashAttention-2. Each K/V staging tensor is at most 64 MiB (2 × 16,384 × 8 KV heads × 128 dimensions × 2 bytes). That bounds one allocation, not total device peak. Fusing the unpack into the long-prefix attention read would remove this staging traffic. The speed benefit on SM86 needs a matched kernel profile and end-to-end cold-prefill measurement. [Packaged source patch](../patches/inkling-sm86.patch)

A contributor also posted RTX 3090 measurements on an earlier experimental build combining three follow-up patches. With UD-IQ4_XS, a 256K context setting and Q8_0 K/V, they reported 772 tok/s prefill, 92.1 tok/s decode and 21,161 MiB peak VRAM. The comment does not give the occupied prefix for the decode timing. The maintainer found position-handling issues on some other cache paths and the author subsequently revised the code. These figures describe the reported revision and test conditions. [3090 measurements and review](https://github.com/unslothai/llama.cpp/pull/407#issuecomment-7084245216)
